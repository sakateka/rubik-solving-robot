# Проектные заметки: распознавание грани кубика Рубика (Rust + YOLO)

**Цель:** приложение на Rust, которое получает кадр с камеры, находит грань
кубика Рубика и определяет цвета 9 стикеров.
**Первый майлстоун:** одна грань → вывод результата текстом.
**Целевое устройство:** Milk-V Duo 256M (SoC SG2002, RISC-V C906 @ 1 ГГц,
256 МБ RAM), камера GC2083 2 МП (MIPI CSI, официальный модуль Milk-V).

---

## Термины текущего этапа

- **Inference (инференс)** — один запуск уже обученной нейросети: входной
  кадр → выходные боксы и вероятности цветов. Не обучение.
- **TPU** — специализированный вычислительный блок SG2002 для нейросетей.
  Наша YOLO-модель выполняется там за ~41 ms, а не на RISC-V CPU.
- **CVI Runtime / `cviruntime`** — библиотека производителя, которая загружает
  `.cvimodel`, выделяет TPU-память и вызывает inference.
- **`.cvimodel`** — формат модели для TPU CV181X/SG2002. Наш файл содержит
  BF16-вариант YOLOv8n; это не PyTorch и не ONNX.
- **BF16** — 16-битный формат чисел для вычислений внутри TPU. Внешний
  интерфейс нашей модели остаётся FP32, то есть Rust передаёт и получает
  обычные 32-битные `float`.
- **FP32** — обычное 32-битное число с плавающей точкой (`f32` в Rust).
- **FFI** — вызов кода на одном языке из другого. В нашем случае Rust вызывает
  маленький C adapter, а он — C API CVI Runtime.
- **ABI** — двоичный договор между кодом и библиотеками: архитектура CPU,
  calling convention, libc и форматы данных должны совпадать. Поэтому binary
  собран под RISC-V musl, а не под x86-хост.
- **musl** — стандартная C-библиотека Linux в образе Duo. Она задаёт dynamic
  loader `/lib/ld-musl-riscv64xthead.so.1` и должна совпадать у binary и SDK.
- **Cross-build** — сборка на x86-ПК программы, которая будет выполняться на
  RISC-V плате.
- **Linker** — этап сборки, соединяющий object-файлы и библиотеки в executable.
  Здесь SDK GCC задаёт RISC-V/musl окружение, а современный LLD разбирает
  RISC-V ISA-атрибуты от Rust.
- **ROI (region of interest)** — фиксированный квадрат интересующей области:
  `(464,32)..(1296,864)` в кадре 1920×1080. Это только грань кубика, без
  дальнего фона и оранжевой детали стенда.
- **Preprocessing** — преобразование кадра в tensor модели. Для текущей
  модели: ROI 832×832 → resize 320×320 → RGB → planar CHW → значения `f32`
  в диапазоне 0…1.
- **RGB planar / CHW** — три цветовых канала хранятся отдельными плоскостями:
  сначала все R-пиксели, затем G, затем B. Это контракт входа YOLO.
- **NMS** — удаление дубликатов боксов. У нас class-agnostic NMS: два
  перекрывающихся бокса считаются дубликатом даже при разных цветах.
- **VI (Video Input)** — драйверный модуль, который забирает кадры с сенсора
  GC2083.
- **ISP (Image Signal Processor)** — аппаратная обработка «сырого» сигнала
  камеры: демозаика, экспозиция, баланс белого, шумоподавление и т.д.
- **VPSS (Video Processing Subsystem)** — аппаратный блок обработки готового
  кадра: crop, resize и преобразования pixel format. Именно он должен убрать
  наш дорогой CPU resize.
- **Vendor media stack / middleware** — набор библиотек CVI (`libvi.so`,
  `libisp.so`, `libvpss.so`, `libsys.so`) и API для управления VI/ISP/VPSS.
  Это не V4L2.
- **`sensor_cfg.ini`** — конфигурация конкретного физического сенсора: тип,
  MIPI-линии, I²C-шина, разрешение и параметры ISP. Для GC2083 штатное место
  на Duo — `/mnt/data/sensor_cfg.ini`; приложение принимает путь явно, чтобы
  не зависеть от current working directory.
- **Camera probe** — минимальная проверочная программа. Она поднимает
  `GC2083 → VI → ISP`, берёт один кадр и сразу его освобождает. Она пока не
  передаёт кадр в модель: это намеренное разделение рисков перед подключением
  VPSS crop/resize и TPU.

### Как мы проверяем двоичные зависимости: `readelf`

`readelf` — утилита из `binutils`, которая читает структуру ELF-файла
(исполняемого файла или `.so` библиотеки), ничего не выполняя. Она нужна здесь
для проверки ABI-зависимостей vendor media stack на уровне, на котором их
увидит dynamic loader платы.

Команда:

```bash
readelf -d duo-buildroot-sdk-v2/cvi_mpi/lib/libsample.so
```

`-d` показывает *dynamic section*. В обычной библиотеке там есть записи вида:

```text
NEEDED               Shared library: [libvi.so]
```

Это означает, что при загрузке данной библиотеки loader обязан также загрузить
`libvi.so`. У собранной SDK `libsample.so` записей `NEEDED` для media-библиотек
нет. Поэтому нельзя полагаться на её транзитивные зависимости: наше
приложение должно явно линковать `libsample.so`, `libvi.so`, `libisp.so`,
`libsys.so`, `libae.so`, `libawb.so`, `libisp_algo.so` и `libsns_gc2083.so`.

Вторая команда:

```bash
readelf -Ws duo-buildroot-sdk-v2/cvi_mpi/lib/libsample.so | rg ' UND '
```

`-W` отключает обрезание длинных строк, `-s` выводит symbol table, а `UND`
означает *undefined*: библиотека вызывает символ, но не содержит его
реализацию. Например:

```text
UND CVI_VI_SetDevBindPipe
UND CVI_ISP_SetPubAttr
UND CVI_VPSS_StopGrp
```

Префиксы показывают владельца API: `CVI_VI_*` реализует `libvi.so`,
`CVI_ISP_*` — `libisp.so`, `CVI_VPSS_*` — `libvpss.so`, `CVI_SYS_*` —
`libsys.so`. Это проверка карты бинарных зависимостей, а не отладка логики
программы.

## 0. Сколько граней нужно засканировать, чтобы узнать раскладку кубика

**Ответ: 5 граней — необходимо и достаточно. На практике сканируем все 6.**

### Почему 5 достаточно

Сканируем 5 граней (все, кроме, например, D). Видно 45 стикеров из 54.
Каждый кубик последнего слоя всё равно однозначно определяется:

- **Рёбра:** у каждого ребра уникальная пара цветов (12 рёбер = 12 различных
  пар). По видимому боковому стикеру ребро опознаётся целиком → цвет его
  стикера на невидимой грани известен.
- **Углы:** видны 2 стикера из 3. Формально остаётся двусмысленность
  (например, видны зелёный и красный → третий цвет белый или жёлтый), но она
  снимается хиральностью углового кубика: порядок цветов на кубике фиксирован
  производителем, и при известной цветовой схеме по двум видимым стикерам и их
  положению третий цвет определяется однозначно.
- Альтернативный взгляд: каждый цвет встречается на кубе ровно 9 раз, поэтому
  мультимножество из 9 невидимых стикеров известно просто подсчётом.

### Почему 4 недостаточно

Контрпример даже для «лучшего» случая, когда невидимые грани противоположны
(сканируем U, D, F, B; не видим R и L). Возьмём собранный куб и поменяем
местами два ребра верхнего слоя (бело-красное ↔ бело-оранжевое) и два ребра
нижнего слоя (жёлто-красное ↔ жёлто-оранжевое), не переворачивая их:

- на U по-прежнему лежат белые стикеры рёбер, на D — жёлтые, F и B не
  изменились → сканы 4 граней идентичны;
- но это другое, причём **легальное** состояние (два обмена = чётная
  перестановка, ориентации не изменились — ограничения группы кубика
  соблюдены).

Различие видно только на гранях R и L, которые мы не сканировали. Значит,
4 грани состояние не определяют. Случай соседних невидимых граней ещё хуже:
там есть углы и рёбра почти без видимых стикеров.

### Почему на практике сканируем все 6

1. **Контроль ошибок:** каждый цвет должен встретиться ровно 9 раз —
   встроенная чексумма против неверно распознанных стикеров.
2. Вывод 6-й грани «по логике» предполагает нулевые ошибки распознавания;
   одна ошибка → неверная дедукция.
3. Не нужен код дедукции/легальности на слабом устройстве.

Вывод для приложения: рабочий процесс — последовательный скан всех 6 граней
с проверкой «9 стикеров каждого цвета» в конце. Первый майлстоун (одна грань)
не меняется.

## 1. Общий пайплайн

```
Камера → Кадр → Препроцессинг → YOLO → Постобработка → Сетка 3×3 → Текст
```

1. **Захват** — один кадр с камеры.
2. **Препроцессинг** — letterbox до 320×320 (сохранение пропорций + поля),
   нормализация пикселей в 0..1, раскладка HWC → CHW.
3. **Инференс** — YOLO возвращает сырую матрицу: для каждого кандидата
   координаты рамки (x, y, w, h) и вероятности 6 классов-цветов.
4. **Постобработка** — фильтр по порогу уверенности + NMS (убираем
   дублирующиеся рамки вокруг одного стикера). Должно остаться ровно 9
   детекций; иначе — явная ошибка/пересъёмка.
5. **Сетка** — сортируем центры рамок по Y, разбиваем на 3 строки, внутри
   строки сортируем по X → матрица 3×3 → текст, например:

```
W W Y
O R R
G B O
```

## 2. Модель

- **YOLOv8n (nano)** — ~12 МБ в fp32, ~3–6 МБ в int8. Для candle есть
  готовый пример инференса YOLOv8.
- **Вход 320×320** вместо 640: в 4 раза меньше вычислений и памяти на
  активации; стикеры крупные — точности хватит.
- **6 классов = 6 цветов** (white, yellow, red, orange, green, blue).
  Каждый стикер — отдельный объект, класс рамки = цвет.
- Экспорт из Ultralytics: ONNX → конвертация в safetensors (для candle).
  При нехватке памяти — int8-квантование.

**Запасной вариант (fallback):** 1 класс «стикер» + определение цвета по
среднему HSV внутри рамки. Разметка проще, устойчивее к освещению.
Переходим на него, если красный/оранжевый или белый/жёлтый будут путаться.

## 3. Данные и обучение

1. **200–500 фото** граней: разные комбинации цветов, освещение (дневное,
   лампа, тень), углы, фоны. Обязательно часть кадров — **с камеры самого
   устройства** (у каждой камеры своя цветопередача).
2. **Разметка:** Label Studio (Docker, studio-start.sh, Local Files storage).
   Бокс вокруг каждого стикера, класс = цвет; порядок классов фиксирован
   атрибутом category="0..5" в XML-конфиге (white=0 ... blue=5, как в
   dataset/data.yaml). Рабочий цикл — model-assisted labeling: размечаем
   вручную часть кадров → обучаем черновую модель → ею предразмечаем
   остальные (tools/import_yolo_predictions.py) → вручную проверяем
   predictions и принимаем (Submit).
3. **Аугментации:** яркость/контраст ±40%, повороты ±15°, лёгкий blur, шум.
   Критично для устойчивости к освещению.
4. **Обучение (на ПК):**
   ```
   yolo train model=yolov8n.pt data=data.yaml imgsz=320 epochs=100
   ```
5. **Экспорт:**
   ```
   yolo export format=onnx imgsz=320
   ```
6. **Валидация** — на фото именно с целевой камеры.

## 4. Стек Rust

| Задача | Выбор | Комментарий |
|---|---|---|
| Инференс | **candle** (pure Rust) | легко кросс-компилируется, маленький бинарь |
| Прототип на ПК | candle или `ort` (ONNX Runtime) | ort зрелый, но тяжёлый и сложен в кросс-компиляции |
| Изображения | `image` | pure Rust, JPEG decode + resize |
| Камера, этап 1 | `sample_sensor_test 2` из SDK → дамп YUV-кадра в /mnt/data | подтверждено по duo-buildroot-sdk-v2 |
| Камера, этап 2 | свой захват через CVI MPI (CVI_VI_GetChnFrame) | v4l2-ноды НЕТ: камера живёт только в vendor-стеке VI/VPSS (cv181x_vi.ko) |

OpenCV не используем вообще — слишком тяжёлый для 256 МБ.

**Кросс-компиляция (ОТЛОЖЕНО):** целевая архитектура под вопросом —
riscv64 (Duo 256M) или ARM. Пока собираем и гоняем только на хосте.
Известная засада на будущее: candle-core тянет `tokenizers` → `onig_sys`
(Си-библиотека) на всех нативных таргетах — при кроссе понадобится
C-тулчейн под цель или отсечение этой зависимости.

**Производительность:** C906 @ 1 ГГц — слабое in-order ядро. YOLOv8n @ 320²
на CPU — порядка секунд на кадр, для статичного стенда приемлемо. Запасной
путь при нехватке скорости: TPU в SG2002 (int8, компиляция модели через
TPU-MLIR в cvimodel + FFI-обёртка к vendor runtime). Это отдельная
оптимизация, не v1.

**Бонус стенда:** фиксированные положение камеры и освещение упрощают и
датасет (меньше вариативности), и сборку сетки 3×3 (положение грани в кадре
постоянно — ожидаемые области стикеров известны заранее, можно использовать
как кросс-чек).

## 7. Этапы работы

1. **Прототип на ПК: ГОТОВ.** Пайплайн работает end-to-end: настоящий
   YOLOv8n на candle грузится из safetensors и детектит на реальных фото
   (проверено на COCO-весах, 80 классов; пиковый RSS ~106 МБ). Юнит-тесты
   на месте. Осталось: заменить COCO-веса на свои 6-классовые (этап 2).
2. **Датасет + обучение: В РАБОТЕ, черновая модель v1 обучена.** 305 кадров
   со стенда (images/), 55 размечены вручную → обучена YOLOv8n (imgsz=320,
   150 эпох, ROCm GPU; `runs/detect/train-rocm`): mAP50=0.995,
   mAP50-95=0.914 (val всего 11 кадров — оценка грубая). Её предсказания
   импортированы в LS как predictions на 250 оставшихся задач (avg score
   0.86; ~114 задач имеют один лишний низкоуверенный бокс conf<0.5 —
   удалить при ревью). Дальше: ревью предразметки → экспорт → сплит 85/15 →
   обучение v2 → конвертер best.pt → safetensors → прогон Rust с --classes 6.
   При следующей предразметке: yolo predict с conf=0.5 (дефолт 0.25 даёт
   лишние слабые боксы).
3. **Интеграция TPU Runtime в приложение.** Сначала небольшой C FFI-слой
   для загрузки `.cvimodel` и вызова `CVI_NN_Forward` из Rust; затем те же
   preprocessing и postprocess, которые уже проверены отдельно.
4. **Захват с камеры и запуск на устройстве.** Подключить GC2083 через
   vendor VI/VPSS, применить фиксированный ROI, измерить полный latency и RSS.
5. **Калибровка в реальном свете**, дообучение на проблемных кадрах.
6. *(Следующий майлстоун)* Скан всех 6 граней → сборка состояния в нотации
   Kociemba (URFDLB) с проверкой «9× каждый цвет» → солвер.

### 7.1. Журнал фактического прогресса — 2026-07-24

Это продолжение исторической записи выше. Там описана первая маленькая v1
модель на 55 кадрах. Она не была ошибкой: именно ею мы предразметили остальные
фотографии и сильно сократили ручную работу. Ниже — что произошло после неё и
почему мы теперь идём к TPU.

#### От фотографий к нормальному датасету

В Label Studio были просмотрены все 305 фотографий. На каждой грани должны
быть девять стикеров, поэтому мы проверили простую, но очень полезную вещь:
в финальных annotations ровно 9 боксов на изображение, всего 2 745 бокса.
Черновики (drafts), которые мешали отображению model predictions, удалили;
сохранённые annotations при этом не трогали.

Финальная разметка лежит в
`project-1-at-2026-07-23-17-40-ecf22cab.zip`. Это экспорт Label Studio в
формате YOLO. В нём есть текстовые labels, но нет исходных фотографий: их
надо брать из `images/`.

Поскольку камера на стенде почти не двигается, мы не стали заставлять модель
смотреть на весь кадр 1920×1080. Справа от кубика есть оранжевая часть корпуса,
которая иногда выглядела для модели как стикер. Поэтому весь процесс — и
обучение, и будущий запуск на устройстве — начинается с одного фиксированного
квадрата:

```text
исходный кадр: 1920×1080
вырезаем:      x=464..1296, y=32..864
получаем:      832×832
```

Этот квадрат выбран по крайним боксам уже размеченных фотографий. Он содержит
весь замеченный люфт куба, но почти не оставляет места фону по X. Если когда-то
физически сдвинуть камеру, это правило надо проверить заново, иначе получится
классическая ошибка: модель училась на одном crop, а на устройстве видит другой.

Сборку датасета делает `src/bin/build_dataset_v2.rs`. Это небольшой Rust
инструмент, а не одноразовый Python-скрипт: он быстро читает исходные PNG,
вырезает ROI, сохраняет удобные для YOLO JPEG quality 95 и пересчитывает
координаты боксов относительно нового квадрата. Он также делит данные не
случайно по одному кадру, а группами соседних shots: почти одинаковые кадры
не должны оказаться одновременно в train и test.

Получился `dataset-v2/`: 215 кадров для обучения, 50 для validation и 40 для
независимого test. Это генерируемая папка, поэтому она не коммитится в git.

#### Что показало обучение

Основную YOLOv8n v2 обучили через Ultralytics на Radeon 8060S с ROCm. Веса
лежат в `runs/detect/train-v2-roi-2/weights/best.pt`. Модель знает
шесть классов цветов и принимает картинку 320×320: наш квадрат 832×832 перед
этим просто уменьшается, без боковых полей.

На validation получилось mAP50-95 = **0.971**. Затем, что важнее, модель
проверили на 40 кадрах, которые не участвовали в обучении и выборе настроек.
Там mAP50-95 = **0.991**, precision = **0.999**, recall = **1.000**. Это не
гарантия вечной работы при любом освещении, но хороший признак, что для нашего
стенда сама идея, ROI и данные работают.

Во время визуального просмотра ONNX-предсказаний увидели редкие маленькие
ложные боксы на фоне. Решение не в том, чтобы просто всё сильнее поднимать
порог: при слишком высоком пороге можно потерять настоящий стикер. Рабочее
правило проверили на всех 40 test-кадрах:

1. сначала отбросить confidence ниже **0.50**;
2. отбросить центры вне ожидаемого поля кубика (`0.05 ≤ x ≤ 0.90`,
   `0.05 ≤ y ≤ 0.95` в координатах crop);
3. сделать **class-agnostic NMS** с IoU=0.5: если красный и оранжевый бокс
   лежат на одном стикере, они должны конкурировать, а не жить рядом;
4. если после этого не ровно 9 боксов — попросить переснять кадр;
5. из девяти центров сделать три строки по Y и отсортировать каждую по X.

С этим правилом все 40 test-кадров дали ровно девять стикеров. Важно не
«взять лучшие девять»: так один ложный бокс мог бы тихо заменить пропущенный
настоящий стикер.

#### Как мы пришли к BF16 TPU-модели

`best.pt` понятен PyTorch, но не TPU платы. Поэтому сначала через Ultralytics
экспортировали его в `best.onnx`: это статическая сеть с входом `[1,3,320,320]`
и выходом `[1,10,2100]`. ONNX прогнали на всех 305 crop-кадрах с нарисованными
боксами, чтобы глазами проверить, что экспорт не сломал детекцию.

В `duo-buildroot-sdk-v2` нашлись runtime и примеры запуска `.cvimodel` на
CV181X, но не компилятор. Для компиляции на хосте скачали Podman-образ
`sophgo/tpuc_dev:latest`, а внутри него установили `tpu_mlir`. Этот контейнер
нужен только на ПК: он превращает ONNX в формат, который понимает TPU SG2002.

Контейнер был создан под именем `rubik-tpu`, поэтому после обычного `exit`
или остановки его не надо скачивать или настраивать заново. Вернуться в него
из корня проекта можно так:

```bash
podman start -ai rubik-tpu
cd /workspace/vision-example/tpu/mlir
```

`start -ai` запускает уже существующий контейнер и подключает текущий терминал
к его shell; установленный внутри `tpu_mlir` остаётся на месте. Если контейнер
когда-либо был именно удалён, а не остановлен, его нужно создать снова
(проект монтируется с хоста, поэтому `tpu/mlir/` и модели не теряются):

```bash
podman run -it --name rubik-tpu \
  -v "$PWD:/workspace/vision-example" \
  -w /workspace/vision-example \
  sophgo/tpuc_dev:latest bash
```

В новом контейнере после этого потребуется снова выполнить `pip install
tpu_mlir`.

Первой командой `model_transform.py` ONNX превратили в
`tpu/mlir/cube_yolov8n_320.mlir`. Одновременно TPU-MLIR прогнал один реальный
кадр через исходный ONNX и через свой FP32 MLIR. Он сравнил 183 внутренних
тензора: ошибок 0, а финальный output совпал с cosine similarity 1.0. Это
важный момент: компилятор действительно понимает наш граф YOLOv8n.

Потом `model_deploy.py` собрал
`tpu/mlir/cube_yolov8n_320_bf16.cvimodel` для `CV181X` — именно так в
TPU-MLIR называется семейство чипа SG2002. Файл весит 6.3 MB и просит у
runtime 8.69 MB непрерывной ION-памяти. Для платы с 256 MB это хороший запас.

При первой попытке мы добавили `--compare_all` и увидели много сообщений
`NOT_SIMILAR` по внутренним слоям. Это не оказалась поломка: BF16 округляет
числа грубее FP32, ошибка понемногу копится по слоям, хотя финальный выход
всё ещё проходит проверку. Поэтому для BF16 сверяем главный output, а не
требуем почти FP32-точности от каждой промежуточной активации.

Мы сознательно остановились на **BF16**, а не на INT8. INT8 был бы меньше и
быстрее, но требует отдельной калибровки и может ухудшить цвета/боксы. Сейчас
памяти BF16 хватает, поэтому разумнее сначала получить работающую качественную
модель на настоящей плате. К INT8 вернёмся только если реальные замеры скорости
или памяти это оправдают.

#### Что делаем дальше и почему именно так

Следующая проверка должна быть максимально скучной и изолированной. Не будем
сразу смешивать камеру, JPEG, crop и Rust. На Duo скопируем три файла:

```text
cube_yolov8n_320_bf16.cvimodel    сама TPU-модель
cube_yolov8n_320_in_f32.npz       уже подготовленный вход одного кадра
cube_yolov8n_top_outputs.npz      эталонный результат для сравнения
```

Штатная программа на плате `model_runner` загружает `.cvimodel`, отправляет
NPZ в TPU и даёт output. Так мы узнаём, что именно **реальный SG2002** способен
загрузить и выполнить модель. Если здесь есть проблема, камера и Rust ни при
чём — искать нужно в runtime или совместимости `.cvimodel`.

Эта проверка уже прошла на Milk-V Duo. Runtime `Cvitek Runtime (1.4.0)`
зарегистрировал cvimodel v1.4, принял вход `images <1,3,320,320>, fp32` и
вернул `output0_Concat_f32 <1,10,2100,1>, fp32`. Сравнение с эталоном прошло:
cosine = 0.999969, correlation = 0.999969, euclidean = 0.992111; все 1/1
выходов прошли порог 0.99. BF16 относится к вычислениям внутри TPU; runtime
осознанно предоставляет внешний input/output как FP32 и делает преобразование
на границе модели.

Следующее измерение всё ещё изолированное: `model_runner --enable-timer`
прогонит уже подтверждённую NPZ-модель много раз и покажет чистую скорость
TPU без камеры, файлового JPEG decode и Rust-кода. Это даст базовую latency,
с которой потом можно сравнить полный пайплайн.

Замер на реальной Duo выполнен: 100 запусков заняли 3 731.65 ms, то есть
**37.316 ms на один TPU inference** и **26.80 FPS**. Это только модель с
готовым входным тензором; финальный end-to-end latency будет включать захват
кадра, ROI, resize/преобразование данных и postprocess. Для статичного
сканирования грани такой запас скорости более чем достаточен, поэтому INT8
сейчас не является приоритетом.

Когда этот минимальный тест пройдёт, будем постепенно возвращать части
настоящего приложения: сначала явный препроцессинг живого кадра (у BF16
baseline пока вход — NPZ), затем маленькую C FFI-обёртку вокруг
`CVI_NN_RegisterModel` / `CVI_NN_Forward` для вызова из Rust, затем GC2083
через VI/VPSS, наш фиксированный ROI и уже проверенную постобработку. После
этого измерим latency и RSS на плате и только тогда решим, есть ли реальная
причина заниматься INT8.

## 8. Подводные камни

- **Освещение:** красный/оранжевый и белый/жёлтый путаются первыми. Лечится
  датасетом с разным светом и фиксированной экспозицией камеры.
- **Блики** на глянцевых стикерах — должны быть в датасете.
- **Не ровно 9 детекций** — обрабатываем явно (пересъёмка / подбор порога
  confidence), не выдаём мусор молча.
- **Сильный угол съёмки** ломает сортировку в сетку — на первом этапе
  требуем фронтальный кадр.
- **Память:** не грузить модель дважды, дропать большие буферы как можно
  раньше.

## 9. Параметры платформы (подтверждено)

1. **Устройство:** Milk-V Duo 256M (SG2002): RISC-V C906 @ 1 ГГц, 256 МБ RAM.
2. **Камера:** GC2083 2 МП (MIPI CSI, официальный модуль Milk-V).
3. **Датасет:** собираем с нуля, стенд готов.
4. **Сборка:** кросс-компиляция с ПК (`riscv64gc-unknown-linux-musl`).

Главный технический неизвестный РЕШЁН (по исходникам duo-buildroot-sdk-v2):
GC2083 живёт в vendor-стеке VI/VPSS (модули cv181x_vi.ko/cv181x_vpss.ko,
грузятся через /mnt/system/ko/loadsystemko.sh), v4l2-ноды нет. Захват:
CVI_VI_GetChnFrame — как в cvi_mpi/sample/sensor_test (дампит YUV в
/mnt/data). Для датасета: YUV→PNG конвертим python'ом (в образе есть
python3+numpy) и забираем по ssh/scp (dropbear в образе есть).

ВАЛИДАЦИЯ нашего YOLOv8 против SDK (tdl_sdk/.../yolov8.cpp): препроцессинг
(factor=1/255, mean=0, RGB planar), DFL (матожидание по 16 бинам),
dist2bbox (grid+0.5, ×stride), sigmoid по классам — всё совпадает с нашей
реализацией. Отличия сознательные: NMS у вендора per-class, у нас
class-agnostic; их cvimodel обрезан до декодера (декод в C++), наш граф
включает декод (как у ultralytics).

### 10.11. Реальный запуск на Milk-V Duo

**Где:** плата, каталог `/mnt/storage` (или другой каталог, куда скопированы
три файла: cvimodel, `cube_yolov8n_320_in_f32.npz` и
`cube_yolov8n_320_board_reference.npz`). Бинарник уже есть в штатном образе:
`/mnt/system/usr/bin/tpu/model_runner`.

Сначала проверка качества:

```bash
/mnt/system/usr/bin/tpu/model_runner \
  --model cube_yolov8n_320_bf16.cvimodel \
  --input cube_yolov8n_320_in_f32.npz \
  --output board-output.npz \
  --reference cube_yolov8n_320_board_reference.npz \
  --tolerances 0.99,0.99,0.99 \
  --verbose 1
```

Успешный результат уже получен:

```text
Inputs:  images <1,3,320,320>,fp32
Outputs: output0_Concat_f32 <1,10,2100,1>,fp32
cosine: 0.999969, correlation: 0.999969, euclidean: 0.992111
Compare Pass.
```

`fp32` здесь — внешний контракт runtime. Модель вычисляется BF16 внутри TPU,
а runtime сам преобразует вход/выход на границе.

Затем чистый замер скорости, уже без reference:

```bash
/mnt/system/usr/bin/tpu/model_runner \
  --model cube_yolov8n_320_bf16.cvimodel \
  --input cube_yolov8n_320_in_f32.npz \
  --output board-output.npz \
  --enable-timer --count 100 --verbose 1
```

Полученный baseline: 100 запусков за 3 731.65 ms, то есть 37.316 ms на
inference и 26.80 FPS. Это скорость только TPU с готовым NPZ-входом.

### 10.12. Начало интеграции TPU Runtime в Rust-приложение

**Где:** хост, из корня репозитория. На этом шаге появились три слоя:
`native/cvi_tpu.c` прячет C API CVI Runtime, `src/tpu.rs` даёт Rust-объект
`CviTpuDetector`, а ветка `--cvimodel` использует тот же ROI и RGB/FP32
preprocessing, что и обученная модель. Камера пока не участвует: входом служит
обычный файл изображения, чтобы не смешивать проблемы VI/VPSS с TPU.

Проверка обычной Rust-ветки и тестов:

```bash
cargo fmt --check && cargo test
cargo run --bin rubik-scan -- --image images/shot_001.yuv.png --stub
```

Результат: 12 тестов прошли, один старый Candle smoke-test остался намеренно
ignored, так как требует отдельные COCO weights. `--stub` дошёл до проверки
NMS и сборки корректной сетки 3×3. Это ещё не тест TPU: без feature Runtime
производственный backend сознательно не собирается на ПК.

Отдельно проверили, что C-обёртка соответствует тем заголовкам CVI Runtime,
которые лежат в SDK:

```bash
cc -std=c11 -Wall -Wextra -Werror -fsyntax-only \
  -Inative \
  -Iduo-buildroot-sdk-v2/cviruntime/include \
  native/cvi_tpu.c
```

Команда успешно завершилась. `-fsyntax-only` важен: он компилирует C-код и
проверяет вызовы `CVI_NN_RegisterModel` / `CVI_NN_Forward`, но не делает
ложную host-сборку для x86 и не пытается линковаться с библиотеками платы.
Следующая проверка будет уже cross-build с `--features cvi-runtime` и
настоящими `libcviruntime.so`/`libcvikernel.so`, собранными этим же SDK.

### 10.13. SDK и C toolchain для cross-build

Исходники SDK находятся в `duo-buildroot-sdk-v2/`. Это Git submodule нашего
репозитория, закреплённый на конкретном commit репозитория
`milkv-duo/duo-buildroot-sdk-v2`. После обычного clone проекта его получают
через `git clone --recurse-submodules`, а в уже существующем checkout — через
`git submodule update --init --recursive`.

В SDK **нет** Git submodule с названием `host-tools`. Это отдельный большой
репозиторий готовых компиляторов, который SDK специально игнорирует в своём
`.gitignore`. Его штатный `build.sh` при отсутствии папки сам делает:

```bash
git clone https://github.com/milkv-duo/host-tools.git host-tools
```

Папка должна лежать именно внутри SDK (`duo-buildroot-sdk-v2/host-tools`),
потому что его scripts ищут RISC-V musl compiler по пути
`$TOP_DIR/host-tools/gcc/riscv64-linux-musl-x86_64`. Мы повторяем только этот
шаг вручную, а не запускаем `./build.sh`: тот после загрузки toolchain начал
бы собирать и упаковывать весь образ платы, что нам не требуется.

Для нашей Duo 256M правильная SDK-конфигурация —
`sg2002_milkv_duo256m_musl_riscv64_sd`. После загрузки toolchain следующий
шаг был выполнен из `duo-buildroot-sdk-v2/`:

```bash
git clone https://github.com/milkv-duo/host-tools.git host-tools

source build/envsetup_milkv.sh
defconfig sg2002_milkv_duo256m_musl_riscv64_sd
build_3rd_party
```

На CMake 4 первая попытка `build_tpu_sdk` остановилась на старом
`cmake_minimum_required` FlatBuffers. SDK менять не нужно. В том же shell
временно определили и **экспортировали** функцию: `export -f` обязателен,
потому что `build_tpu_sdk` запускает дочерний Bash-скрипт.

```bash
cmake() {
  case "$1" in
    --build|--install|--version) command cmake "$@" ;;
    *) command cmake -DCMAKE_POLICY_VERSION_MINIMUM=3.5 "$@" ;;
  esac
}
export -f cmake

build_tpu_sdk
```

`build_3rd_party` готовит внешние зависимости, а `build_tpu_sdk` собирает
согласованные для этой конфигурации `cviruntime` и `cvikernel`. Он не шьёт
плату и не собирает полный firmware image. Сборка завершилась с кодом `0`.
Итоговый SDK находится в:

```text
duo-buildroot-sdk-v2/install/soc_sg2002_milkv_duo256m_musl_riscv64_sd/
  tpu_musl_riscv64/cvitek_tpu_sdk/
```

Проверены два главных артефакта:

```text
lib/libcviruntime.so  — ELF 64-bit RISC-V shared object
lib/libcvikernel.so   — ELF 64-bit RISC-V shared object
```

Они и musl RISC-V compiler из `host-tools` станут входом для Cargo cross-build
нашего приложения.

### 10.14. Современный linker для Rust и старый SDK toolchain

Первая Cargo cross-build дошла до линковки, то есть заголовки, C-обёртка и
поиск `cviruntime` уже были настроены правильно. Она остановилась на GNU `ld`
из Xuantie toolchain: он слишком стар, чтобы разобрать современные RISC-V ISA
метки (`zifencei`), которые текущий Rust ставит в объектных файлах. Это не
ошибка модели и не несовместимость самой платы.

На хост был установлен пакет **`lld`** (LLVM linker; не отладчик `lldb`):

```bash
sudo apt install lld
```

После установки появился `/usr/bin/ld.lld`. Его используем только для
финальной линковки Rust, сохранив SDK GCC как C compiler и поставщика musl
sysroot. `scripts/build-duo.sh` создаёт в `target/duo-lld/` ссылку `ld.lld`, а
`scripts/duo-linker.sh` вызывает SDK GCC с `-B... -fuse-ld=lld`. Это сочетание
даёт современный парсер RISC-V ISA-атрибутов, но не меняет ABI, CRT или
библиотеки целевой Duo.

### 10.15. Первая cross-build Rust-приложения с TPU Runtime

Для сборки не нужно вручную вызывать `cc`: `build.rs` вызывает его сам через
crate `cc`, когда включена feature `cvi-runtime`. Внешний скрипт нужен только
для target-окружения: он проверяет SDK, задаёт RISC-V C compiler, библиотечные
пути и linker-wrapper с LLD.

**Где:** хост, корень проекта.

```bash
bash scripts/build-duo.sh
```

Внутри это эквивалентно Cargo-команде:

```bash
cargo build --release \
  --target riscv64gc-unknown-linux-musl \
  --features cvi-runtime \
  --bin rubik-scan
```

Сборка завершилась успешно. Получен файл:

```text
target/riscv64gc-unknown-linux-musl/release/rubik-scan
```

Проверка `file` показала: RISC-V 64-bit PIE, musl dynamic loader
`/lib/ld-musl-riscv64xthead.so.1`, stripped, размер 2.2 MB. Его прямые
зависимости — `libcviruntime.so`, `libgcc_s.so.1` и `libc.so`; `libcvikernel`
подтягивается самой `libcviruntime.so`. Следующий тест должен выполняться уже
на Duo: подать приложению исходный кадр 1920×1080 и `.cvimodel`, чтобы
одновременно проверить Rust FFI, реальный TPU и наш ROI/preprocessing.

### 10.16. Первый end-to-end запуск приложения на Milk-V Duo

На Duo были скопированы RISC-V binary, BF16 cvimodel и исходный (не cropped)
кадр `shot_051.yuv.png`. Запуск:

```bash
./rubik-scan \
  --image shot_051.yuv.png \
  --cvimodel cube_yolov8n_320_bf16.cvimodel \
  --conf 0.5 \
  --iou 0.5
```

Успешный результат: после class-agnostic NMS осталось ровно 9 боксов;
получена сетка и compact state `ROROROROR`:

```text
R O R
O R O
R O R
```

Тем самым подтверждён весь путь на реальном устройстве: PNG decode → fixed
ROI → RGB planar FP32 → Rust/C FFI → CVI Runtime → BF16 TPU → YOLO decode →
confidence/central gate/NMS → grid sort. В штатном образе отсутствует `ldd`;
это не влияет на проверку, поскольку приложение успешно загрузило Runtime и
выполнило inference.

Повторная проверка на другом исходном кадре `shot_010.yuv.png` также дала
ровно 9 детекций с confidence 0.94–0.98 и без ложных боксов. Полученная грань:

```text
G B Y
O O Y
Y O Y
```

Compact state: `GBYOOYYOY`.

### 10.17. Измерение полного file pipeline и переход к камере

На Duo добавлен флаг `--timings`; он измеряет стадии текущего запуска с PNG.
Для `shot_010.yuv.png` получено:

```text
decode       517.39 ms
preprocess   262.96 ms
model_load    32.97 ms
inference     40.95 ms
postprocess    0.27 ms
total        866.06 ms
```

Вывод однозначный. TPU и postprocess не являются проблемой: 41 ms inference
согласуется с отдельным baseline `model_runner` (~37 ms). `model_load` тоже
не критичен, потому что в нормальном camera-процессе модель регистрируется
один раз при старте, а не на каждый кадр. Текущие 866 ms почти полностью
тратятся на временный путь «PNG с диска → CPU decode → CPU resize».

Следующая задача — заменить именно этот путь, а не оптимизировать его:

```text
GC2083 → VI → ISP → VPSS (ROI crop + resize) → model input → TPU
```

На работающем образе подтверждены нужные динамические библиотеки:
`libvi.so`, `libisp.so`, `libvpss.so`, `libsys.so`, `libsns_gc2083.so`, а
также `libcviruntime.so` и `libcvikernel.so`. Значит vendor camera stack на
плате присутствует.

Что ещё надо аккуратно проверить перед написанием camera backend: каким
pixel format VPSS выдаст 320×320 кадр и как сохранить текущий контракт модели
`RGB planar + FP32 / 255`. Runtime умеет принимать device/video frames, но
его API не делает crop/resize сам; за это отвечает VPSS. Нельзя заявлять
zero-copy заранее: сначала надо подтвердить совпадение выходов camera/VPSS
и уже проверенного file pipeline на одном и том же кадре.

### 10.18. Первый camera milestone: VI/ISP probe

Перед интеграцией камеры собраны media-библиотеки из SDK. Это делается на
хосте, из `duo-buildroot-sdk-v2/`; команды не прошивают плату и не меняют
rootfs, а только создают RISC-V `.so` для cross-linker:

```bash
source build/envsetup_milkv.sh
defconfig sg2002_milkv_duo256m_musl_riscv64_sd

make -C cvi_mpi module -j"$(nproc)"
make -C cvi_mpi/sample/common -j"$(nproc)"
make -C cvi_mpi/component/isp/sensor/sg200x gcore_gc2083 -j"$(nproc)"
make -C cvi_mpi/component/isp/sensor/sg200x gcore_gc4653 ov_ov5647 -j"$(nproc)"
make -C cvi_mpi/modules/bin -j"$(nproc)"
```

Последние три артефакта потребовались потому, что SDK sample source содержит
generic sensor/configuration path: при линковке ему нужны
`libsns_gc2083.so`, `libsns_gc4653.so`, `libsns_ov5647.so` и
`libcvi_bin.so`. На целевом образе эти библиотеки уже присутствуют.

В проект добавлен отдельный binary `rubik-camera-probe`. Его C adapter
(`native/cvi_camera.c`) использует CVI API, а Rust-обёртка
(`src/bin/rubik-camera-probe.rs`) только передаёт параметры и печатает
метаданные одного кадра. Инициализация проходит так:

```text
sensor_cfg.ini → VI/ISP init → получить один VI frame → напечатать размер,
pixel format, stride → освободить frame → корректно остановить VI/ISP/SYS
```

Для этого adapter не линкуется с монолитной `libsample.so`: та содержит код
всех vendor demos (VENC, VO, RGN и т.д.) и делает зависимости непрозрачными.
`build.rs` компилирует только нужные SDK source units (`sample_common_sys`,
`platform`, `vi`, `isp`, `sensor`, `bin`, `sensor_list`) с backend GC2083.
Это делает зависимость приложения ограниченной именно camera lifecycle.

`libcvi_ispd2.so` в SDK намеренно оставляет optional JSON/bin hooks
unresolved. Поэтому `scripts/duo-linker.sh` передаёт LLD
`--allow-shlib-undefined` — только для unresolved references *в vendor shared
libraries*. Неопределённый symbol из нашего C/Rust кода остаётся ошибкой
линковки.

Кросс-сборка обоих приложений выполняется одной командой:

```bash
scripts/build-duo.sh
```

Она завершилась успешно. Получены:

```text
target/riscv64gc-unknown-linux-musl/release/rubik-scan
target/riscv64gc-unknown-linux-musl/release/rubik-camera-probe
```

Проверка `readelf -d rubik-camera-probe` подтвердила прямые зависимости на
`libvi.so`, `libisp.so`, `libsys.so`, `libcvi_bin.so`, `libae.so`,
`libawb.so` и `libsns_gc2083.so`; они есть в установленном образе Duo.

Первый запуск на плате, после копирования нового binary в `/mnt/storage`:

```bash
export LD_LIBRARY_PATH=/mnt/system/lib:/mnt/system/usr/lib:/mnt/system/usr/lib/3rd

./rubik-camera-probe --sensor-config /mnt/data/sensor_cfg.ini
```

Ожидаемый успешный результат — строка вида:

```text
VI frame: 1920x1080, pixel_format=..., stride=[...], length=[...]
```

Этот шаг проверяет только сенсор и lifecycle vendor media stack. После него
следующая работа — подключить VPSS и получить аппаратно cropped/resized
320×320 ROI, затем сравнить его preprocessing с уже проверенным PNG path.
