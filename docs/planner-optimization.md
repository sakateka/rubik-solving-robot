# Оптимизации планировщика движений (move_planner)

Статус: утверждено к реализации
Дата: 2026-08-20

## Контекст и ограничения

Механика стенда: 4 гриппера (L/R/T/B), 4 rail'а. Гриппер имеет 3 ориентации:
FrameParallel (P), FramePerpendicular (⊥), FrameParallelReversed (PR).
Поворот грани = поворот гриппера в parallel при закрытом rail'е.
Flush = regrip гриппера в perpendicular: open rail → ⊥ → close rail
(3 шага, ~3.4с).

Ограничения безопасности (подтверждены владельцем железа):

1. **Custody**: всегда хотя бы одна противоположная пара rail'ов в NearGrip
   (кроме шагов открытия стенда в конце execute-пути).
2. **Collision (консервативно)**: любые два СОСЕДНИХ гриппера в parallel
   (P или PR) при обоих закрытых rail'ах = столкновение. Направление
   складывания когтей не учитываем — модель подтверждена как консервативная.
3. Смежность — полный двудольный граф K2,2: каждый LR-гриппер соседствует
   с каждым TB-гриппером. Следствие: перед любым поворотом одной группы все
   грипперы другой группы обязаны быть в ⊥ → **look-ahead с отложенным
   flush бесполезен** (flush неизбежен в той же точке, deferral лишь
   переносит его в конец без экономии). Ветка закрыта.
4. Rail'ы можно открывать при грипперах в ЛЮБОЙ ориентации (parallel или
   perpendicular) — подтверждено на железе.

### 1. Frame-tracking планировщик

restore_front нужен только для финальной ориентации куба (подтверждено).
Значит между F/B блоками остаёмся в переориентированном фрейме.

После position_front_back стенд в том же механическом состоянии
(все ⊥, все rail'ы закрыты), куб повёрнут вокруг вертикальной оси.
В фрейме RotatedFB напрямую поворачиваются U, D, F, B:

| Logical | Physical gripper |
|---------|------------------|
| F       | Right            |
| B       | Left             |
| U       | Top              |
| D       | Bottom           |

L/R в этом фрейме недоступны → выход через restore_front.

Направления поворотов (CW/CCW/Half) сохраняются: маппинг F→Right, B→Left
уже существует и проверен на железе; U/D — физически та же операция, что в
canonical (logical U остаётся на physical Top).

Инварианты автомата:

- перед любым поворотом группы другая группа должна быть clean/⊥;
- одновременно dirty может быть только одна группа;
- при переходе в `RotatedFB` и из него `T/B` должны быть clean/⊥ до
  поворота куба; если это не так, сначала выполняется `flush_group(TB)`;
- `U/D` во вращённом фрейме не являются бесплатными: перед ними всё равно
  выполняется flush LR, если LR dirty; аналогично перед следующим F/B
  выполняется flush TB, если TB dirty;
- `Frame` и dirty-state обновляются вместе с каждым emitted step, а не только
  на границах логических ходов.

Автомат:

| Ход | Canonical                    | RotatedFB                       |
|-----|------------------------------|---------------------------------|
| F/B | вход: flush TB + fused pf    | lazy turn (как сейчас в блоке)  |
| U/D | как сейчас                   | остаёмся во фрейме              |
| L/R | как сейчас                   | выход: flush TB + fused rf      |

Конец последовательности: если во фрейме — выход зависит от Finish.

Экономия: −13.6с за каждую устранённую пару `rf+pf` между двумя F/B-блоками,
разделёнными только ходами U/D. Например, `F U` не экономит пару
переориентаций, а `F U B` экономит одну пару.
Худший случай (F/B строго чередуются с L/R) — не хуже текущего.

### 2. Слияние граничных flush с pf/rf (fused boundaries) — реализовано

Сейчас flush_group(LR) закрывает LR, а pf/rf тут же открывают их заново.
Слияние в один заход:

```
open LR → ⊥(dirty L/R) → поворот куба (T/B в P/PR) → close LR → open TB → ⊥T/B → close TB
```

Два РАЗДЕЛЬНЫХ SetGrippers: сначала L/R в ⊥, потом вращение куба
(не вращаем куб со сложенными когтями L/R).

Экономия: −2.4с (пара close+open) на вход при dirty LR, −2.4с на выход
для завершённого F/B-блока (ходы блока пачкают L/R). Итого пара границ
сегмента даёт −2.4…−4.8с. Например `F B` (held): 19 → 17 шагов.

ВАЖНО — корректность: flush TB перед pf и перед rf ОБЯЗАТЕЛЕН.
Поворот T/B из ⊥ в P/PR и есть поворот куба на 90°; из dirty-состояния
получится 180° и состояние куба испортится. Это не безопасность, а
корректность механики.

### 3. Режимы завершения плана (Finish)

- **Finish::CanonicalHeld** (held-путь, ручные ходы): финальный rf + flush,
  куб остаётся в canonical ⊥. Поведение held_execute_steps не меняется.
- **Finish::Release** (execute-путь, solve→open): если open идёт после
  solve — НЕ восстанавливаем каноничный фронт и НЕ флашим (подтверждено
  владельцем):
  - конец в RotatedFB → сразу open: экономия примерно −7.8с, если последний
    ход был F/B, или до −10.2с, если перед завершением dirty была TB;
  - конец в Canonical → skip последнего flush: −3.4с для непустой
    последовательности (или 0 для пустой).

Безопасность: append_open_steps открывает LR первым; до открытия TB custody
  сохраняется через TB. После начала финального release custody больше не
  проверяется, а collision проверяется до `AllOff`; после открытия LR
  столкновение невозможно при любом состоянии T/B.

## Ожидаемая экономия

- Каждая устранённая пара `rf+pf` между F/B-блоками: −13.6с
- Пара fused-границ одного F/B-сегмента: −2.4…−4.8с
- Финал в execute: примерно −3.4…−10.2с в зависимости от dirty-группы
  и текущего frame.
- Итоговую экономию не фиксировать заранее диапазоном: её нужно считать по
  фактической calibration и тем же 10 Cube20-последовательностям. Текущие
  замеры в `docs/PROJECT_NOTES.md` показывают порядок около 3 минут на один
  20-ходовый план, поэтому оценка `60–90с` не является baseline для этого
  стенда.

## Что НЕ делаем (отклонено при анализе)

- Same-face coalescing (R R' → ∅): min2phase уже устраняет same-face пары
  внутри Solution::append_move — на выходе солвера их не бывает.
- Look-ahead / deferred flush: бесполезен при консервативной модели
  столкновений (см. ограничение 3).
- Параллельное выполнение rail+gripper в одном шаге: риск для механики.
- Пропуск restore_front в held-пути: финальная ориентация куба нужна.

После реализации обновить соответствующий раздел `docs/PROJECT_NOTES.md`:
solver `Execute` больше не обязан возвращать canonical front перед normal
open; canonical endpoint остаётся контрактом только для held/manual-пути.
